Five things a bot needs to know before it buys

Every call runs all five against Base mainnet at the current block. One request, one answer.

aCan it be sold

A buy and a sell are simulated with eth_call state overrides against the best pool (Uniswap v2/v3/v4, Aerodrome). If the sell reverts, that is the strongest risk signal the API has.

bBuy & sell tax

Measured from the simulation, not read from the source. The round-trip loss (fees, hook taxes, slippage) is reported next to it.

cOwner powers

Whether ownership is renounced, and whether the contract exposes mint, blacklist, pause, fee setters, trading switches or limit setters. Detects EIP-1967 and similar upgradeable proxies.

dLiquidity

Exit depth in USD across pools, and whether the LP tokens are burned, locked by a known launchpad (Clanker, Zora), or unknown.

eToken age

How long ago the contract was created, plus creator signals: share of supply held, repeat deployers, fresh wallets.

A label, a score, and the reasons in plain English

Your bot branches on one field. You read the reasons when it says no.

SAFEscore 75–100

Buy and sell simulate cleanly and no abusive owner controls were found. It does not mean the price will hold.

CAUTIONscore 45–74

Tradeable, but with risk signals such as taxes, active owner powers, thin liquidity or an upgradeable proxy.

DANGERscore below 45, or any critical signal

For example a failed simulated sell, a tax of 50% or more, or no pool on the supported DEXes.

Three lines. The third one pays.

The 402 response is the sign-up: it tells your client what to pay and where.

shell
curl {{API_URL}}/v1/sample                        # 1. free: see the response shape
curl -i {{API_URL}}/v1/verdict/0xTOKEN            # 2. HTTP 402 + USDC payment terms
node check.mjs 0xTOKEN                            # 3. signs the 402, retries, prints the verdict
  1. The sample and health endpoints need nothing.
  2. The 402 response carries the price, the USDC asset on Base and the pay-to address in its PAYMENT-REQUIRED header (base64 JSON). Any x402 client can read it.
  3. check.mjs is the short script below. It uses the standard @x402/fetch client, so the wallet only signs a USDC transfer authorization for the exact price.
check.mjs (JavaScript, ~10 lines)
check.mjs · npm i @x402/fetch @x402/evm viem
import { wrapFetchWithPaymentFromConfig } from "@x402/fetch";
import { ExactEvmScheme } from "@x402/evm";
import { privateKeyToAccount } from "viem/accounts";

// use a dedicated wallet that holds a few dollars of USDC on Base
const account = privateKeyToAccount(process.env.EVM_PRIVATE_KEY);
const pay = wrapFetchWithPaymentFromConfig(fetch, {
  schemes: [{ network: "eip155:8453", client: new ExactEvmScheme(account) }],
});

const res = await pay(`{{API_URL}}/v1/verdict/${process.argv[2]}`);
console.log(JSON.stringify(await res.json(), null, 2));

Or add it to your agent as a remote MCP server

Claude, Cursor and most other clients cannot pay x402 themselves; there the tool returns the payment terms and the paid HTTP URL instead of a verdict, and nothing is charged.

How payment works. Payment is in USDC on Base through the x402 protocol: the server keeps no accounts or keys, a facilitator verifies and settles each payment. Results are cached for 60 seconds per address.

What this is not

  • Heuristics, not advice. The output is automated on-chain risk signals. It is not financial advice and not an audit. A SAFE verdict means no mechanical trap was detected at that block, not that the price will hold or that the token cannot be rugged later.
  • A snapshot. An owner who keeps powers can change the token after the check. Re-check before large trades; results are cached for 60 seconds.
  • Base mainnet only. Chain 8453, and ERC-20 tokens traded on Uniswap v2/v3/v4 or Aerodrome pools. Tokens that trade elsewhere may show as having no pool.
  • The simulation is one size. The buy is simulated at roughly $20. Large orders can face more slippage, and some Uniswap v4 hooks treat a same-transaction buy and sell differently from a later sale; those cases can produce false positives or false negatives.
  • Some facts are unknowable from the chain. LP lock status is often "unknown" for position-NFT liquidity. Off-chain signals (team, social, off-DEX transfers) are not looked at.
  • Mechanics, not intent. The API reports signals for an address. It does not say who is behind a token or whether anyone meant harm.
  • Early service. Engine 0.1.0, one operator, no uptime guarantee. A free /v1/health endpoint shows whether the service can reach the chain.
